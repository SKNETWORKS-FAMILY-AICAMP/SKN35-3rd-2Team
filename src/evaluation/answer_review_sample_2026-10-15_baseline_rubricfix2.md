## R05 (회차 2, answerable)

**질문**: 개발 중에 loopback 주소를 제외한 http:// URL을 사용하지 말아야 하는 이유는 무엇인가요?

**답변**

loopback 주소를 제외한 HTTP URL을 사용하지 말아야 하는 이유는 주로 보안과 네트워크 구성의 관점에서 설명할 수 있습니다.

1. **보안 문제**: 외부에서 접근 가능한 HTTP URL을 사용하면, 악의적인 사용자가 해당 URL을 통해 시스템에 접근할 수 있는 위험이 있습니다. 특히, 인증이나 권한 관리가 제대로 이루어지지 않는 경우, 데이터 유출이나 서비스 거부 공격(DoS) 등의 위험이 증가합니다.

2. **네트워크 구성**: loopback 주소(예: 127.0.0.1)는 로컬 시스템을 가리키며, 외부 네트워크와의 연결 없이 테스트 및 개발을 할 수 있게 해줍니다. 외부 URL을 사용하면 네트워크 지연이나 연결 문제로 인해 개발 및 테스트 과정에서 예기치 않은 오류가 발생할 수 있습니다.

3. **환경 일관성**: 개발 환경에서 loopback 주소를 사용하면, 코드가 다른 환경(예: 테스트, 프로덕션)으로 이동할 때 환경 간의 일관성을 유지할 수 있습니다. 외부 URL을 사용하면 각 환경에 맞는 URL을 관리해야 하므로 복잡성이 증가합니다.

결론적으로, loopback 주소를 사용하면 보안과 네트워크 안정성을 높이고, 개발 및 테스트의 일관성을 유지할 수 있습니다.

**항목 판정**
- [ ] 1. loopback 주소를 제외한 http:// URL 사용을 금지하는 이유를 설명한다. → met (답변은 loopback 주소를 제외한 HTTP URL 사용을 금지하는 이유를 보안 문제, 네트워크 구성, 환경 일관성의 관점에서 설명하고 있다.)
- [ ] 2. OAuth 2.1의 요구사항을 안내한다. → not (답변에서 OAuth 2.1의 요구사항에 대한 언급이 없다.)
- [ ] 3. 개발 및 테스트 시 명시적인 옵트아웃 메커니즘을 제공해야 함을 설명한다. → not (답변에서 개발 및 테스트 시 명시적인 옵트아웃 메커니즘에 대한 설명이 없다.)
- [ ] 4. 사설 IP 범위에 대한 요청 차단을 안내한다. → not (답변에서 사설 IP 범위에 대한 요청 차단에 대한 언급이 없다.)
- [ ] 5. 내부 리소스에 대한 리다이렉트 검증을 강조한다. → not (답변에서 내부 리소스에 대한 리다이렉트 검증에 대한 강조가 없다.)

## R01 (회차 2, answerable)

**질문**: subagents를 사용할 때, LangGraph가 이들을 정적으로 발견할 수 없는 이유는 무엇인가요?

**답변**

LangGraph가 subagents를 정적으로 발견할 수 없는 이유는 주로 subagents의 동적 생성 및 실행 방식 때문입니다. 

1. **정적 분석의 한계**: LangGraph는 코드의 정적 분석을 통해 구조를 이해하고, 이를 기반으로 그래프를 생성합니다. 그러나 subagents는 런타임에 동적으로 생성되거나 호출될 수 있기 때문에, 정적 분석 시점에서는 이들의 존재를 알 수 없습니다.

2. **동적 의존성**: subagents는 특정 조건이나 이벤트에 따라 생성될 수 있으며, 이러한 동적 의존성은 정적 분석 도구가 파악하기 어렵습니다. 예를 들어, 특정 입력이나 상태에 따라 다른 subagent가 호출될 수 있습니다.

3. **유연한 아키텍처**: subagents는 다양한 방식으로 구성될 수 있으며, 이로 인해 LangGraph가 모든 가능한 subagent의 경로를 미리 정의하기 어렵습니다. 이는 코드의 유연성을 높이지만, 정적 분석의 정확성을 떨어뜨립니다.

결론적으로, subagents의 동적 특성과 런타임 의존성 때문에 LangGraph는 이들을 정적으로 발견할 수 없습니다.

**항목 판정**
- [ ] 1. subagents가 도구 함수 내에서 호출되기 때문에 LangGraph가 정적으로 발견할 수 없음을 설명한다. → partial (답변은 subagents가 동적으로 생성되고 실행되는 이유를 설명하지만, LangGraph가 도구 함수 내에서 호출되기 때문에 정적으로 발견할 수 없다는 점은 언급하지 않았다.)
- [ ] 2. subagents는 지속적인 대화 기록을 유지하지만, LangGraph는 이를 정적으로 인식하지 못함을 안내한다. → not (subagents가 지속적인 대화 기록을 유지하지만 LangGraph가 이를 정적으로 인식하지 못한다는 내용이 포함되어 있지 않다.)
- [ ] 3. get_state 함수가 서브그래프와 함께 사용할 때 서브에이전트 상태를 반환하지 않는 이유를 설명한다. → not (get_state 함수가 서브그래프와 함께 사용할 때 서브에이전트 상태를 반환하지 않는 이유에 대한 설명이 없다.)
- [ ] 4. 서브에이전트 상태를 읽어야 할 경우, 사용자 정의 그래프의 노드 함수에서 서브에이전트를 호출해야 함을 안내한다. → not (서브에이전트 상태를 읽어야 할 경우, 사용자 정의 그래프의 노드 함수에서 서브에이전트를 호출해야 한다는 안내가 없다.)
- 금지 위반: 없음
- 관련성: partial, Faithfulness: 0.000

## R13 (회차 3, answerable)

**질문**: 클라이언트가 메타데이터 문서를 사용할 때, 서버가 클라이언트 ID와 리디렉션 URI를 어떻게 검증하는지 구체적으로 설명해 줄 수 있나요?

**답변**

클라이언트가 메타데이터 문서를 사용할 때, 서버가 클라이언트 ID와 리디렉션 URI를 검증하는 과정은 다음과 같습니다.

1. **클라이언트 ID 등록**: 클라이언트는 인증 서버에 등록되어 있어야 하며, 이 과정에서 클라이언트 ID와 함께 리디렉션 URI도 등록됩니다.

2. **리디렉션 URI 검증**: 인증 서버는 요청받은 리디렉션 URI가 사전에 등록된 URI와 정확히 일치하는지 검증합니다. 이는 리디렉션 공격을 방지하기 위한 필수적인 절차입니다.

3. **신뢰할 수 있는 URI 확인**: 인증 서버는 리디렉션 URI가 신뢰할 수 있는 URI인지 확인해야 합니다. 신뢰할 수 없는 URI로의 리디렉션을 방지하기 위해, 인증 서버는 사용자가 올바른 결정을 내릴 수 있도록 사용자에게 알릴 수 있습니다.

이러한 검증 절차는 보안상의 이유로 매우 중요하며, 클라이언트와 서버 간의 신뢰를 유지하는 데 기여합니다.

자세한 내용은 [Authorization Security Considerations 문서](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)에서 확인할 수 있습니다. 

추가적으로, OAuth 2.1의 리디렉션 URI 검증에 대한 내용을 더 알고 싶다면, OAuth 2.1의 관련 섹션을 살펴보는 것도 좋습니다.

**항목 판정**
- [ ] 1. 클라이언트 ID가 URL 형식일 때 서버가 메타데이터 문서를 가져오는 과정을 설명한다. → partial (클라이언트 ID 등록 과정에 대한 설명은 있으나, URL 형식일 때 서버가 메타데이터 문서를 가져오는 과정에 대한 설명이 없다.)
- [ ] 2. 가져온 문서의 client_id가 해당 URL과 정확히 일치하는지 검증해야 한다(MUST)고 설명한다. → partial (리디렉션 URI 검증에 대한 설명은 있으나, client_id가 해당 URL과 정확히 일치하는지 검증해야 한다는 명시적인 설명이 없다.)
- [ ] 3. 서버가 인가 요청의 리디렉션 URI를 메타데이터 문서에 있는 목록과 비교하여 검증하는 절차를 설명한다. → partial (리디렉션 URI 검증에 대한 설명은 있으나, 인가 요청의 리디렉션 URI를 메타데이터 문서에 있는 목록과 비교하여 검증하는 절차에 대한 구체적인 설명이 부족하다.)
- [ ] 4. 메타데이터 문서가 유효한 JSON 구조이고 필수 필드를 포함하는지 확인한다고 안내한다. → not (메타데이터 문서가 유효한 JSON 구조이고 필수 필드를 포함하는지 확인한다는 내용이 전혀 언급되지 않았다.)
- 금지 위반: 없음

## R24 (회차 3, answerable)

**질문**: 노드 함수를 정의할 때 GraphNode와 State.Node의 차이점은 무엇이며, 각각의 사용 사례는 어떻게 되나요?

**답변**

노드 함수를 정의할 때 `GraphNode`와 `State.Node`의 차이점은 다음과 같습니다.

### 1. 정의
- **GraphNode**: 일반적으로 그래프 구조에서 사용되는 노드를 나타냅니다. 이 노드는 다른 노드와의 연결(엣지)을 통해 그래프를 형성하며, 각 노드는 데이터와 함께 연결 정보를 포함할 수 있습니다.
- **State.Node**: 주로 상태 머신이나 상태 관리 시스템에서 사용되는 노드를 나타냅니다. 이 노드는 특정 상태를 나타내며, 상태 간의 전환을 관리하는 데 사용됩니다.

### 2. 사용 사례
- **GraphNode 사용 사례**:
  - 소셜 네트워크에서 사용자 간의 관계를 나타내는 그래프를 구성할 때.
  - 경로 탐색 알고리즘(예: 다익스트라 알고리즘)에서 노드를 사용하여 최단 경로를 찾을 때.
  
- **State.Node 사용 사례**:
  - 게임 개발에서 캐릭터의 상태(예: 대기, 이동, 공격)를 관리할 때.
  - UI 애플리케이션에서 사용자 인터페이스의 상태(예: 로딩, 오류, 완료)를 관리할 때.

### 3. 동작 방식
- **GraphNode**는 연결된 다른 노드와의 관계를 통해 그래프의 구조를 형성하고, 이를 통해 다양한 알고리즘을 적용할 수 있습니다.
- **State.Node**는 상태 전환을 통해 시스템의 동작을 제어하며, 각 상태에서 수행할 작업을 정의할 수 있습니다.

이 두 노드는 각각의 목적에 맞게 설계되었으며, 사용되는 맥락에 따라 적절한 선택이 필요합니다.

추가적으로, 그래프 이론이나 상태 머신에 대한 더 깊은 이해를 원하신다면, 그래프 알고리즘이나 상태 머신 패턴에 대해 알아보는 것도 좋습니다.

**항목 판정**
- [ ] 1. GraphNode의 정의와 사용 사례를 설명한다. → met (GraphNode의 정의와 사용 사례를 설명하고 있다.)
- [ ] 2. State.Node의 정의와 사용 사례를 설명한다. → met (State.Node의 정의와 사용 사례를 설명하고 있다.)
- [ ] 3. GraphNode와 State.Node의 차이점을 비교한다. → met (GraphNode와 State.Node의 차이점을 비교하고 있다.)
- [ ] 4. 각각의 사용 사례를 구체적으로 안내한다. → met (각각의 사용 사례를 구체적으로 안내하고 있다.)
- 금지 위반: 없음
- 관련성: direct, Faithfulness: 0.000

## R03 (회차 1, answerable)

**질문**: 부모 그래프에서 .stream() 메소드를 사용할 때, 서브그래프의 출력을 포함하려면 어떤 설정을 해야 하나요?

**답변**

부모 그래프에서 `.stream()` 메소드를 사용할 때 서브그래프의 출력을 포함하려면, 서브그래프를 정의하고 이를 부모 그래프에 추가해야 합니다. 아래는 그 과정을 설명하는 코드 예시입니다.

1. **서브그래프 정의**: 서브그래프의 상태를 정의하고, 노드와 엣지를 추가합니다.
2. **부모 그래프 정의**: 부모 그래프의 상태를 정의하고, 서브그래프를 부모 그래프의 노드로 추가합니다.

다음은 이를 구현한 코드입니다:

```python
from langgraph.graph import START, StateGraph
from typing import TypedDict

# Define subgraph
class SubgraphState(TypedDict):
    foo: str  # note that this key is shared with the parent graph state
    bar: str

def subgraph_node_1(state: SubgraphState):
    return {"bar": "bar"}

def subgraph_node_2(state: SubgraphState):
    return {"foo": state["foo"] + state["bar"]}

subgraph_builder = StateGraph(SubgraphState)
subgraph_builder.add_node(subgraph_node_1)
subgraph_builder.add_node(subgraph_node_2)
subgraph_builder.add_edge(START, "subgraph_node_1")
subgraph_builder.add_edge("subgraph_node_1", "subgraph_node_2")
subgraph = subgraph_builder.compile()

# Define parent graph
class ParentState(TypedDict):
    foo: str

def node_1(state: ParentState):
    return {"foo": "hi! " + state["foo"]}

builder = StateGraph(ParentState)
builder.add_node("node_1", node_1)
builder.add_node("node_2", subgraph)  # Add the subgraph as a node
builder.add_edge(START, "node_1")
builder.add_edge("node_1", "node_2")
```

이 코드는 서브그래프를 부모 그래프에 통합하여 `.stream()` 메소드를 사용할 때 서브그래프의 출력을 포함할 수 있도록 설정합니다. 

추가적으로, 서브그래프의 이벤트를 스트리밍하는 방법에 대한 예시는 다음과 같습니다:

```python
stream = graph.stream_events({"foo": "foo"}, version="v3")  # [!code highlight]

for subgraph in stream.subgraphs:
    print(subgraph.graph_name, subgraph.path)

    for snapshot in subgraph.values:
        print(subgraph.path, snapshot)
```

이 코드는 서브그래프의 이름과 경로를 출력하고, 각 스냅샷의 값을 출력합니다.

이와 관련하여 더 알아볼 만한 주제로는 "서브그래프의 상태 관리"나 "이벤트 스트리밍 최적화"가 있습니다.

**항목 판정**
- [ ] 1. 부모 그래프에서 .stream() 메소드를 사용할 때 서브그래프 출력을 포함하려면 설정을 안내한다. → partial (답변은 서브그래프를 부모 그래프에 추가하는 방법을 설명하고 있지만, subgraphs 설정을 true로 변경해야 한다는 내용이 포함되어 있지 않음.)
- [ ] 2. subgraphs 설정을 true로 변경해야 함을 설명한다. → not (streamMode 설정이 'updates'로 되어야 한다는 설명이 없음.)
