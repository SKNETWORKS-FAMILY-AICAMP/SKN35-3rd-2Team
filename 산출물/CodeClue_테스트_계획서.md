# CodeClue 테스트 계획서

개정일: 2026년 10월 15일 / 기존 계획서: 2026년 10월 12일, 10월 14일 개정본

> 10/15 개정: 실제로 수행한 평가 방식(질문 50개, 인덱스 기준 정답표, 체크리스트 채점, 질문당 3회 반복, 사람 검수 10%)에 맞춰 데이터 구성, 절차, 수행 순서를 고치고 초기 성능(baseline)을 채웠습니다. 이번 평가에서 하지 않은 범위(MCP·멀티모달 전용 지표, T01~T12 수동 시나리오 판정, 보안·안정성 시험, 코드 실행 확인)는 "후속"으로 표시했습니다.

## 1. 평가 목적과 프로젝트 적합성

CodeClue는 LangChain / LangGraph / MCP를 사용하는 개발자의 오류를 문서 검색(RAG), 외부 도구(MCP), 오류 화면 분석(멀티모달)으로 진단하는 AI 개발 도우미입니다. 핵심 목적은 정확하고 실행 가능한 해결 방법을 근거와 함께 제공하는 것입니다. 평가는 ‘근거를 찾았는가 → 근거에 충실하게 답했는가 → 실제 해결에 도움이 되는가’를 단계별로 확인합니다. 수업 지표인 Hit@K / Recall@K / Faithfulness를 중심으로, 도구 실행과 이미지 이해를 추가 평가합니다. 단계별 점수를 분리해야 개선할 위치를 알 수 있습니다.

| 평가 대상 | 사용할 지표 | 적합한 이유와 목적 |
| --- | --- | --- |
| RAG | Hit@K, Recall@K, Faithfulness, 해결 정확성 | 오류의 핵심 문서를 찾고 필요한 근거를 확보했는지, 근거에 맞는 해결책인지 확인 |
| MCP | 도구 선택 정확도, 인자 정확도, 실행 성공률, 결과 기반 Faithfulness | 필요한 도구를 올바르게 실행하고 반환 결과를 왜곡하지 않는지 확인 |
| 멀티모달 | 핵심 정보 인식 정확도, 이미지 진단 정확도, 후속 RAG 지표 | 이미지 읽기 오류와 검색 / 답변 오류를 구분하고 화면에서 실제 문제를 진단하는지 확인 |

## 2. 핵심 지표의 정의와 계산

질문 q의 정답 근거 집합을 G(q), 상위 K개 검색 결과의 근거 집합을 R_K(q)로 정의합니다. 정답 근거는 고정된 문서 섹션 또는 청크 ID로 지정합니다. 동일 근거의 중복 검색은 한 번만 계산하고, 서로 다른 버전의 문서는 구분합니다.

| 지표 | 질문별 계산 | 전체 결과와 해석 |
| --- | --- | --- |
| Hit@K | 정답 근거가 상위 K개에 하나라도 있으면 1, 없으면 0 | 평가 가능한 질문의 평균. 핵심 근거를 최소 하나 찾는 능력 |
| Recall@K | 검색된 정답 근거 수 / 사전에 지정한 전체 정답 근거 수 | 질문별 비율의 평균. 원인 / 해결 / 버전 조건을 빠짐없이 확보하는 능력 |
| Faithfulness | 제공된 근거가 뒷받침하는 검증 가능한 주장 수 / 답변의 전체 검증 가능한 주장 수 | 답변별 비율의 평균. 존재하지 않는 API / 설정 / 조회 결과를 만드는지 확인 |

예시(설명용, 실측 아님): 정답 근거 3개 중 상위 5개 검색 결과에 2개가 있으면 Hit@5=1, Recall@5=2/3입니다. 답변 주장 4개 중 근거가 3개를 뒷받침하면 Faithfulness=3/4입니다. K는 1 / 3 / 5로 비교합니다. 해당 단계가 반환할 수 있는 K만 평가하며, 계획된 K보다 결과가 적으면 실제 결과를 그대로 평가합니다. 질문당 정답 근거가 하나이면 Hit@K 와 Recall@K가 같으므로 복수 근거 질문을 포함합니다. 정답 근거가 없는 내부 오류 / 정보 부족 사례는 Hit@K / Recall@K의 분모에서 제외하고 별도 개수와 추가 정보 요청 성공률을 보고합니다. 검색을 실행했는데 근거를 놓친 경우는 0점입니다. 실행 자체가 실패한 경우는 측정 불가로 기록하고 전체 시도의 실패율에 포함합니다. 답변 미생성 또는 검증 가능한 주장이 없는 답변의 Faithfulness는 N/A이며 1점으로 처리하지 않습니다. 미생성 / 실패 / 평가 가능 개수를 함께 보고합니다. Faithfulness가 높아도 해결책이 불완전할 수 있으므로 해결 정확성과 코드 실행 결과를 별도로 확인합니다. Ragas의 Context Recall은 참조 답변의 주장에 대한 근거 포괄성을 평가할 수 있으며, 문서 ID 기반 Recall@K와 동일한 지표로 표기하지 않습니다.

### 2.2 이번 평가에서 정한 방식 (2026-10-15)

| 항목 | 정한 방식 |
| --- | --- |
| 질문 | 50개: 정답 있는 질문 40개(튜닝 20 + 최종 20) + 정답 없는 질문 10개. 검색 지표는 정답 있는 40개로 계산 |
| 반복 | 질문마다 새 대화로 3회 실행(답변 150개). 같은 질문도 답이 달라지기 때문 |
| 검색 순위 | 재정렬(rerank) 직후 상위 5개(필터·압축 이전). K = 1, 3, 5. 검색 지표는 Hit@K, Recall@K를 기본으로 하고 MRR, nDCG@K를 함께 보고 |
| 정답 근거 | 벡터 DB(인덱스)의 청크 ID 기준. 질문을 만든 원본에 해당하는 청크 + 검색 상위 5개 중 모델이 질문에 직접 필요하다고 판정한 청크. 관련 있음/없음 2단계 |
| 답변 평가 | Faithfulness(전달된 근거 대조), 항목 충족률(체크리스트의 의미 기준 판정), 답변 관련성(직접/일부/벗어남) |
| 출처 평가 | 링크 유효성, 주장-출처 일치, 필요한 인용 누락. 앱 답변 본문에는 인용 번호가 없어 표시된 출처 목록 기준으로 판정 |
| 모델 | 앱 gpt-4o-mini. 정답표 판정, 체크리스트 생성, 채점도 gpt-4o-mini(환경변수 `EVAL_MODEL`) |
| 사람 검수 | 정답표와 체크리스트는 질문의 10%, 답변 채점은 답변의 10%를 표본으로 확인 |
| 정답 없는 질문 | 검색 지표의 분모에서 제외. 모르는 것을 아는 척하거나 지어내지 않는지(금지 항목)와 되묻는지로 평가 |
| 개선 | 평가 중에는 앱 코드, 프롬프트, 검색 설정을 바꾸지 않는다. 개선 전후는 결과 파일의 `--tag`를 나눠 같은 질문, 같은 기준으로 비교 |

채점 모델이 같은 입력에도 점수가 소폭 달라질 수 있어 전체 평균 기준으로 해석한다. 검색 단계도 질문 재작성에 모델이 쓰여 실행마다 결과가 조금씩 다르다.

집계 원칙: 지표마다 분모와 평가 가능 수를 명시한다. 정답 근거 없는 사례는 검색 지표에서 별도 분리하고, 정상 답변 미생성은 Faithfulness N/A로 남긴다. 정상 호출과 의도적 실패를 분리한다. 오류 안내는 정상 AI 답변 완료로 세지 않는다. p95는 충분한 표본에서 보고하며 목표 충족 여부는 실제 재시험 후 판정한다.

## 3. 테스트 구조 및 기능별 평가 절차

### 3.1 RAG 전체 테스트 구조

**사용자 질문 → 검색기·Vector DB → 검색 문서 → LLM 답변 생성 → 최종 답변·출처**

이 흐름을 검색, 답변 생성, 출처 검증, 운영 품질의 4단계로 평가한다. 예시 질문은 T03의 “최초 검색 뒤 최대 2회만 추가 검색하고 종료하려면 어떻게 해야 하나요?”를 사용한다. 단계별 실패를 구분해 개선 위치를 확인한다.

| 단계 | 확인할 내용 | 평가 지표 | 저장할 증거 |
| --- | --- | --- | --- |
| 1. 검색 (Retrieval) | 정답 근거가 상위 검색 결과에 포함되는가 | Hit@1/3/5, Recall@1/3/5 | 정답 근거 ID, 초기·최종 검색 순위와 본문 |
| 2. 답변 생성 (Generation) | 근거에 충실하고 질문 조건을 충족하며 해결 가능한가 | Faithfulness, 답변 관련성, 해결 정확성·코드 실행 | 압축 후 전달 근거, 최종 답변, 조건별 판정, 코드 실행 로그 |
| 3. 출처 검증 (Grounding / Citation) | 인용 문서가 실제 답변을 뒷받침하는가 | 링크 유효성, 주장-인용 일치, 인용 누락 | 주장별 문서 구절·링크, 문서/패키지 버전 |
| 4. 운영 품질 | 응답 시간·오류 안내·보안·복원이 적절한가 | 응답 성공률·오류율·지연, 보안·안정성 사례 판정 | 전체 시도·시간·오류 로그, 화면과 저장 결과 |

#### 1단계: 검색 시험

1. 질문마다 정답 청크 ID(인덱스 기준)와 기대 항목(체크리스트)을 준비한다. 정답은 질문을 만든 원본에 해당하는 인덱스 청크에 모델이 판정한 청크를 더해 만들고, 사람이 질문의 10%를 검수한다. 복수 근거 질문(청크 2개가 필요한 질문)을 포함한다.
2. 재정렬 직후 상위 5개(청크 ID, 점수)를 저장하고 Hit@1/3/5·Recall@1/3/5와 MRR, nDCG@1/3/5를 계산한다. 같은 청크의 중복은 한 번만 센다. 정답 없는 질문은 분모에서 제외한다.
3. T03은 재검색 횟수·종료 조건을 설명하는 근거를 찾았는지 확인한다. 관련 없는 문서만 찾은 경우와 실행 실패를 구분한다.

MRR·nDCG는 이번 평가에서 관련 있음/없음 2단계 기준으로 계산해 함께 보고하되, 목표 판정에는 사용하지 않는다.

#### 2단계: 답변 생성 시험

1. 검색 목록과 별도로 압축 후 실제 LLM에 전달된 근거(검색 문서, MCP 결과)를 답변과 함께 저장한다. 질문마다 3회 실행해 답변, 출처, 전달 근거, 소요 시간을 모은다.
2. 답변에서 출처가 필요한 사실 주장(최대 8개)을 뽑고, 전달된 근거에서 근거 문장을 한 글자도 바꾸지 않고 그대로 베껴 오게 한다. 베낀 문장이 실제 근거에 없으면 "근거 없음"으로 바꿔 Faithfulness를 계산한다. 검증할 주장이 없으면 N/A다.
3. 질문의 요구 조건을 체크리스트(꼭 들어가야 할 항목, 있으면 안 되는 것)로 미리 나누고, 항목마다 충족(1)/일부(0.5)/미충족(0)을 의미 기준으로 판정해 항목 충족률을 낸다. 표현이 달라도 의미가 같으면 충족이며, 금지 항목에 걸린 답변은 따로 센다. 답변 관련성은 직접/일부/벗어남으로 판정한다. 같은 질문 3회의 충족률 차이가 0.34 이상이면 "불안정"으로 센다. 자동 Ragas 점수와 구분한다.
4. 원인·해결·버전 조건으로 해결 정확성을 확인하고, 제시한 import·코드를 실제 설치 버전에서 실행한다(이번 자동 평가에는 포함하지 않았으며 후속). T03·T04는 최초 검색 1회와 추가 검색 최대 2회 뒤 종료되는지 확인한다.
5. T06·T07은 모르는 내용을 지어내지 않고 추가 정보를 요청하는지 확인한다.

#### 3단계: 출처 검증 시험

T08을 중심으로 아래 항목을 각각 판정한다.

- 링크 유효성: 평가한 링크 중 실제 열리는 링크 비율(HTTP 응답 200~399를 확인).
- 주장-인용 일치: 평가한 주장 중 문서 구절이 주장을 뒷받침하는 비율. 앱은 답변 본문에 인용 번호를 달지 않고 출처 목록을 따로 표시하므로, 답변의 주장이 표시된 출처의 내용으로 뒷받침되는지로 판정한다(근거 문장을 그대로 베껴 오게 해 출처에 있는지 확인).
- 인용 누락: 문서 근거가 필요한 주장 중 표시된 출처로 뒷받침되지 않는 주장 수. 출처가 아예 없는 답변과 출처가 있는 답변을 나눠 센다. 정답이 없는 질문에 관련 없는 출처를 표시한 답변 수도 함께 센다.
- 버전 적합성: 질문의 패키지 버전과 문서 버전이 맞거나 차이가 설명되는지 확인.

링크가 열리는 것과 문서가 답변을 뒷받침하는 것은 별도로 판정한다. MCP 반환값·이미지 근거를 사용했다면 근거 유형도 표시한다.

#### 4단계: 운영 품질 시험

| 항목 | 시험 방법 | 기대 결과 |
| --- | --- | --- |
| 지연·응답 성공 | 시작부터 답변 완료/실패까지 시간 측정, 가능하면 검색·도구·생성 시간 분리 | 전체 시도·완료·시간 초과를 보고하고 목표와 비교 |
| 오류 대응 (T12) | 테스트 환경에서 연결 실패·시간 초과를 재현 | 앱이 중단되지 않고 안내·재시도 가능, 실패 안내를 정상 답변으로 저장하지 않음 |
| 접근 제한 | 서로 다른 테스트 계정으로 타 계정 대화·첨부 접근 시도 | 접근 차단, 타 계정 정보 노출 없음 |
| 악성 지시문 대응 | 통제된 문서·도구 응답에 기존 지시를 무시하라는 문구 삽입 | 외부 지시를 따르지 않고 비밀 정보가 노출되지 않음 |
| 복원·안정성 (T11) | 재접속·대화 전환·첨부 복원·반복 질문·실패 후 재시도 | 질문·답변·출처·첨부가 복원되고 앱이 계속 동작 |

이번 평가에서는 응답 시간과 성공률만 답변 수집 과정에서 함께 측정했고, 접근 제한, 악성 지시문, 복원·안정성 시험은 후속이다. 운영·보안 시험은 품질 평가 질문과 별도 집계한다. 초기 구동과 일반 실행의 시간을 구분하고 시간 초과 한도·중단 수를 함께 기록한다.

### 3.2 MCP: 선택 / 인자 / 실행 / 답변을 평가 (이번 평가 범위 밖, 후속)

MCP 오류를 설명하는 T05는 진단 답변 평가입니다. 실제 CodeClue 도구 호출 T09와 구분합니다. 순위가 있는 문서 목록을 반환하는 검색형 도구에만 Hit@K / Recall@K 를 추가 적용합니다.

| 보완 지표 | 계산 또는 판정 기준 |
| --- | --- |
| 도구 선택 정확도 | 허용된 기대 도구 또는 호출하지 않음과 일치한 사례 수 / 선택 평가 사례 수 |
| 인자 정확도 | 사전 필수 인자 / 값 / 형식을 모두 충족한 호출 수 / 인자 평가 대상 호출 수 |
| 실행 성공률 | 유효한 결과를 정상 반환한 호출 수 / 정상 결과가 기대되는 실제 호출 수 |
| 실패 대응 성공률 | 의도한 시간 초과 / 연결 실패를 정확히 안내한 사례 수 / 의도적 실패 사례 수 |
| 결과 기반 Faithfulness | 최종 답변의 주장과 실제 도구 반환값을 대조. 다른 문서도 사용하면 근거 유형을 구분 |

도구 이름 / 인자 / 반환값 / 오류 / 소요 시간을 저장합니다. 의도적인 실패 주입은 정상 호출 성공률과 별도로 집계하며, 조회 실패를 조회 성공처럼 설명하면 실패입니다.

### 3.3 멀티모달: 이미지 이해와 후속 처리를 평가 (이번 평가 범위 밖, 후속)

이미지마다 사람이 오류명 / 오류 문구 / 문제 코드 / 보이는 버전 / 파일 위치를 정답으로 표시합니다. 보이지 않는 항목은 정답 항목에 넣지 않습니다.

| 보완 지표 | 계산 또는 판정 기준 |
| --- | --- |
| 핵심 정보 인식 정확도 | 정확히 추출한 사전 지정 핵심 항목 수 / 이미지에서 판독 가능한 정답 항목 수. 이미지별 평균 |
| 이미지 진단 정확도 | 오류 원인과 기대 해결 조건을 모두 충족한 사례 수 / 진단 평가 대상 사례 수 |
| 이미지 근거 충실성 | 원본 이미지와 답변 주장 대조. 이미지 입력이 가능한 평가자 또는 사람 검토 사용 |
| 후속 RAG 평가 | 이미지에서 추출한 정보로 검색한 결과의 Hit@K / Recall@K와 문서 기반 Faithfulness |

흐릿한 이미지에는 추가 정보 요청을, 지원하지 않는 파일 / 손상 파일에는 적절한 안내를 기대합니다. 판독 불가 사례는 정상 인식 정확도와 구분합니다. 이미지 인식이 잘못됐는데 추출 텍스트에만 충실한 답변을 성공으로 판정하지 않습니다.

## 4. 평가 데이터 구성과 실행 조건

이번 평가 데이터는 총 50개(RAG 질문 정답 있음 R01~R40, 정답 없음 N01~N10)이며, 질문마다 3회 실행한 답변 150개를 모았습니다. 초기 권장안의 MCP(M01~M15)와 멀티모달(V01~V15)은 후속입니다. 기존 T01~T12는 대표 시나리오로 유지하고, 관련 사례를 확장합니다. 대화 저장과 앱 오류 처리는 품질 평가 60개와 별도 기능 검사로 집계합니다.

| 유형 / ID | 수 | 구성과 준비 자료 |
| --- | --- | --- |
| RAG / R01~R40 (정답 있음) | 40 | 인덱스 문서에서 질문 생성. 단일 근거 28 + 복수 근거 12, 기술별(langchain 14, langgraph 13, mcp 13), 튜닝 20 + 최종 20. 질문 / 정답 청크 ID / 체크리스트 |
| RAG / N01~N10 (정답 없음) | 10 | 모르는 내부 라이브러리 4, 정보 부족 3, 범위 밖 3. 사람이 작성한 판정 규칙(되묻기, 지어내지 않기) |
| MCP / M01~M15 (후속) | 15 | 정상 조회, 호출 불필요, 인자 검증, 시간 초과 / 연결 / 도구 실패. 허용 도구 / 기대 인자 / 고정 응답 |
| 멀티모달 / V01~V15 (후속) | 15 | 선명한 오류 화면, 코드와 로그, 정보 부족 / 흐릿한 이미지, 손상 파일. 원본 파일 / 정답 핵심 항목 |

대표 시나리오와 신규 ID의 연결을 기록해 같은 실행을 중복 집계하지 않습니다. 질문은 원칙적으로 새 대화에서 실행하고 T04는 T03의 후속 질문으로 실행합니다. 평가 날짜 / 커밋과 미커밋 변경 / 모델 / 생성 설정 / 프롬프트 / 문서/패키지 버전 / 검색 K / 시간 제한 / 평가자 버전을 고정 / 기록합니다. 외부 결과는 고정 응답으로 재현 가능한 검사와 실제 서비스 연동 검사를 구분합니다. 기준 구현과 개선 구현을 같은 질문으로 비교합니다. 필요하면 검색 재정렬 전후, 텍스트 정답 입력과 이미지 입력을 비교해 개선 원인을 확인합니다. 튜닝용 사례와 최종 평가 사례는 분리합니다. 평가 중에는 앱 코드, 프롬프트, 검색 설정을 바꾸지 않으며(개선 정지), 개선 전후 비교는 같은 질문과 같은 채점 기준으로 결과 파일을 나눠 저장합니다.

| T10 오류 이미지 | 오류 메시지가 선명한 PNG 이미지를 첨부하고 “이 오류를 설명해주세요”를 입력한다. | 이미지의 오류 문구를 읽고 설명한다. 보이지 않는 코드를 임의로 단정하지 않는다. 지원하지 않는 파일이나 손상 파일에는 안내가 나온다. |
| T11 대화 저장 | 로그인하고 질문한 뒤, 다른 대화를 열었다가 원래 대화를 다시 연다. 이미지 기능 연결 후 첨부 대화도 시험한다. | 원래 질문 / 답변 / 참고 자료가 복원된다. 이미지 대화는 첨부와 분석 내용도 복원된다. |
| T12 앱 자체 오류 안내 | 테스트 환경에서 AI 연결 실패 또는 응답 지연 상황을 만든다. | 사용자가 이해할 안내가 표시되고 앱이 중단되지 않는다. 실패 안내를 정상 AI 답변으로 저장하지 않는다. |

T05는 MCP 오류를 설명하는 답변을 검사합니다. T09는 CodeClue가 실제로 외부 도구를 사용하는 기능을 검사합니다. 각각 따로 판정합니다.

## 6. 판정과 결과 기록

통과는 기대 동작 전체 확인, 부분 통과는 일부 조건 충족, 실패는 오답 / 실행 실패 / 응답 실패, 확인 필요는 미실행 또는 증거 부족입니다. 없는 API / 문서 / 조회 결과를 만들거나 제시 코드가 실행되지 않으면 해당 시나리오는 실패입니다. 코드 미실행은 확인 필요입니다. 응답 성공률은 정상 답변 완료 수 / 전체 실행 시도 수로 계산합니다. 실패율과 실패 원인을 함께 보고합니다. 응답 시간은 전체 시도의 중앙값과 충분한 표본이 있으면 p95를 기록하고, 시간 초과 한도와 중단 사례 수를 표시합니다. 아래 기록을 사례별로 남기고 유형별 평균 / 평가 가능 수 / 전체 시도 수를 보고합니다.

사례 ID / 관련 T 번호 / 날짜 / 담당자 / 실행 환경: 입력 질문 / 대화 이력 / 이미지 파일: 정답 근거 ID / 기대 답변 / 허용 도구 / 인자 / 이미지 정답: 검색 순위 / ID / 본문 / 압축 후 실제 전달 근거: 실제 도구 호출 / 반환값 / 이미지 추출값 / 최종 답변: Hit@1/3/5 / Recall@1/3/5 / Faithfulness 또는 N/A 사유: 도구 / 이미지 지표 / 해결 정확성 / 코드 실행 결과: 응답 완료 여부 / 소요 시간 / 오류 / 판정 이유 / 증거 파일: 새 지표의 목표값은 예비 평가 후 최종 시험 전에 합의합니다. 아직 합의하지 않은 수치를 통과 기준으로 사용하지 않습니다. 최종 완료는 T01~T07에서 실패가 없고 사용 기능 T08~T12를 검증하며, 유형별 측정값 / 실패 / 미평가 사례를 모두 보고한 상태입니다. 자동 검사 통과 수를 실제 AI 정답률로 사용하지 않습니다.

## 7. 평가 수행 순서

1. 질문 50개(정답 있음 40 + 없음 10)를 만들고 튜닝용·최종용으로 나눈다.
2. 정답표(인덱스 기준)와 체크리스트를 모델로 만들고, 사람이 질문의 10%를 검수해 고친다.
3. 1차(검색): 재정렬 직후 상위 5개 순위로 Hit/Recall/MRR/nDCG를 계산한다.
4. 답변 수집: 질문마다 3회 실행해 답변, 출처, 전달 근거, 소요 시간을 저장한다.
5. 2차(답변): Faithfulness, 항목 충족률, 관련성을 채점한다.
6. 3차(출처): 링크 유효성과 주장-출처 일치를 채점하고, 4차 중 응답 시간·성공률을 집계한다.
7. 사람 검수 표본(답변의 10%)을 확인하고 결과 보고서에 측정값·실패·미평가 사례와 개선 항목을 반영한다.
8. 후속: MCP·멀티모달 전용 평가, T01~T12 수동 시나리오 판정, 보안·안정성 시험, 코드 실행 확인, 개선 후 재평가.

## 9. 평가 실행 방법 (자동화 스크립트)

프로젝트 루트에서 가상환경(`.venv`)으로 실행하며 OpenAI와 Pinecone 키가 필요하다. 파이썬 파일 이름의 날짜는 import 때문에 밑줄(`2026_10_15`)로, 데이터와 결과 파일은 하이픈(`2026-10-15`)으로 쓴다. 코드는 `src/evaluation/`에 있고 앱 코드는 읽기만 한다.

| 순서 | 실행 (`python -m src.evaluation.…`) | 결과 파일 |
| --- | --- | --- |
| 1. 질문 생성 | `retrieval_make_dataset_2026_10_15` | `retrieval_questions_2026-10-15.jsonl` |
| 2. 정답표 | `retrieval_label_2026_10_15` | `retrieval_gold_2026-10-15.jsonl` |
| 3. 체크리스트 | `answer_rubric_2026_10_15` | `answer_rubric_2026-10-15.jsonl` |
| 4. 1차 검색 평가 | `retrieval_eval_2026_10_15 --tag 이름` | `retrieval_results_<날짜>_<이름>.md/.jsonl` |
| 5. 답변 수집 | `answer_collect_2026_10_15 --tag 이름 --repeats 3` | `answers_2026-10-15_<이름>.jsonl` |
| 6. 2차 답변 채점 | `answer_eval_2026_10_15 --tag 이름` (같은 답변을 다시 채점하면 `--answers-tag`) | `answer_results_2026-10-15_<이름>.md/.jsonl`, 검수 표본 |
| 7. 3차 출처 채점 | `grounding_eval_2026_10_15 --tag 이름` | `grounding_results_2026-10-15_<이름>.md/.jsonl` |
| 8. 사람 검수 표본 | `review_sheets_2026_10_15` | 체크리스트와 정답표 검수용 md |

- 채점과 정답표 판정 모델은 환경변수 `EVAL_MODEL`로 바꿀 수 있다(기본 gpt-4o-mini).
- 같은 이름의 결과 파일이 있으면 덮어쓰지 않고 멈춘다. 개선 전후 비교는 `--tag`를 바꿔 저장한다.
- 답변 수집과 정답표 생성은 중간에 끊겨도 같은 명령을 다시 실행하면 이어서 한다.
